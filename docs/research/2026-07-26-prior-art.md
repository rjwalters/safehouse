# Research 3 — Prior-art scan: has anyone built safehoused? (2026-07-26)

Deep-research pass (5 phases, 103/103 agents, 24/25 claims confirmed). Question: does anything already
implement safehoused's pattern — one Matrix device, many keyless agent personas behind it, local
dispatch — so we don't reinvent it?

## Verdict: BUILD FRESH on matrix-rust-sdk; CRIB baibot/mxlink; rebuild pantalaimon's shape

**No project implements the "one device, many keyless agent personas, local-socket dispatch"
multiplexing daemon.** The nearest things either multiplex *users/tokens* (each with its own device),
or run *one bridge per single agent*. There is **no "someone already built this, stop" red flag.**

## The closest living starting point

**Fork/crib `baibot` + `mxlink`** for the persistent-E2E headless-bot skeleton (headless login, at-rest
encrypted SQLite crypto store, key backup/restore on matrix-rust-sdk), and **rebuild pantalaimon's
proxy shape** (daemon owns the device, clients hold no keys) and **Hermes's decrypt-and-dispatch
pattern** (daemon decrypts inbound, forwards plaintext to a keyless local agent) — but generalized to
**one device multiplexing many personas over a unix socket**, which none of them do.

## Design validation (nice)

A verified finding *confirms* our core choice: **sharing one access token across multiple independent
crypto clients breaks E2E** (mautrix: "multiple clients using the same token can cause issues with
encryption... no longer allowed"). That is exactly *why* safehoused centralizes ALL crypto in one
daemon process and keeps agent personas keyless — the design is the correct response to that
constraint, not a violation of it. (The mautrix *relay-mode* "one puppet, many senders,
displayname-prefix" claim was refuted 1-2 and excluded — don't cite it.)
